### Week 1 (Aug 10–16) — Inference path + Qwen3 setup · exit: latency < 500 ms

### Week 5 (Sep 7–13) — PDM v2 · exit: baseline drift shows variance

Started early, 2026-08-08 — the blocking prerequisite ("an adapter must exist to calibrate against") was already satisfied by Week 2's `modern_r16_a32_policeofficer` adapter, so no reason to wait for the calendar week.

- [x] **Built `evaluation/pdm_v2.py`** — five feature families instead of one archaic-word-list: (1) **lexicon** — per-archetype distinctive vocabulary computed TF-IDF-style from the real 659-entry dataset (`build_archetype_lexicons()`), not hand-picked; (2) **register** — fixed informal (`gonna/wanna/ain't/...`) vs formal (`therefore/hereby/...`) markers, archetype-independent; (3) **formality** — contraction-density bucket; (4) **syntax** — sentence-length + question-presence buckets; (5) **stance** — hedging vs assertive language. Combined into one feature set per response, same Jaccard-based drift formula PDM v1 used (`single_turn_drift_v2()`) — the aggregation math wasn't the broken part, the single word-list was.
- [x] **Calibrated against real generations, not the dataset** — `evaluation/run_pdm_v2_calibration.py`: 15 real police-officer prompts (sampled across both the hand-authored and SODA-sourced entries, not just the first N), generated via the actual GGUF path, baseline (stock TinyLlama) vs `modern_police` adapter.
  - **Acceptance technically met:** baseline stdev=0.0376 (mean 0.8880, range 0.80–0.92), adapter stdev=0.0103 (mean 0.9173, range 0.88–0.92) — neither is the flat, saturated 0.9833-everywhere failure mode. Real variance exists in both conditions.
  - **Real problem found, not hidden: the ordering is backwards.** The adapter (mean drift 0.9173) scores *worse* than the untrained baseline (mean drift 0.8880), despite the adapter's outputs being obviously better in-character on manual read (*"Just a routine traffic stop, nothing to worry about."*) versus the baseline's meta-commentary artifacts (*"Sure, here's a possible response: NPC: (voice breaking with emotion)..."*). Root cause: the reference feature set is a 25-feature union across the whole archetype's training data, and Jaccard's denominator is dominated by that fixed-size reference — a **short, correctly terse, in-character response has fewer feature slots to hit than a long rambling one**, so brevity gets penalized as drift regardless of actual persona quality. This directly contradicts the earlier finding that in-game NPC lines should be short (`Docs/TODO.md` Week 1 optimization plan).
  - **Not patched blind under time pressure** — this needs a real design decision (length-normalize the Jaccard denominator? weight families instead of pooling into one set? cap per-family match count?) before PDM v2 is trustworthy for the Weeks 9–10 headline α-sweep. Flagged for the user, not silently fixed.
- [x] **Round 2 fix: score each family separately, then average (user decision).** Removed the single pooled feature set — each of the 5 families now gets its own Jaccard, averaged across families. Result: **fixed the length-bias, did not fix the ordering.** Adapter still scored worse (mean 0.8824) than baseline (mean 0.8702), and now the acceptance criterion *failed* too (adapter stdev=0.0034, essentially flat).
  - **Second real problem found via per-family diagnostic breakdown, not guessed:** `formality`/`syntax`/`stance` reference sets were a *union* of every bucket value seen across 134 training entries — for a 3-valued attribute like formality, the union hits all 3 possible buckets almost immediately, so Jaccard(response's one bucket, {all 3 buckets}) is a **constant** regardless of what the response says. Two of five families (register, stance) were contributing zero signal for this exact reason; lexicon was near-zero too, but for the separate, legitimate reason that short responses rarely hit a sparse 15-word archetype vocabulary.
- [x] **Round 3 fix: mode-matching for the three categorical families** (formality/syntax/stance compare against the archetype's single most-common value per attribute, not the union). Real variance came back (baseline stdev=0.0988, adapter stdev=0.0828) — **but the ordering was still backwards.** Per-family breakdown pinpointed exactly why: `formality` mean drift was 0.667 (baseline) vs 0.933 (adapter) — the adapter's contraction-heavy, terse speech ("I'll", "it's", "I'm") didn't match the archetype's formality *mode* ("high" — few contractions).
  - **Third real problem, and this one was about the data, not the code:** checked the actual formality distribution behind that mode — `{high: 62, low: 53, medium: 19}` out of 134. "High" barely edges out "low" as the single most common value; the archetype is genuinely close to bimodal. Binary mode-matching was treating 53/134 (40%) of the archetype's own legitimate training variation as flatly "wrong."
- [x] **Round 4 fix: distributional typicality instead of binary mode-match.** Reference for formality/syntax/stance is now `{value: observed_frequency / peak_frequency}` per attribute — landing on the mode still scores 1.0, landing on a substantial secondary value (like "low" formality, 53/62 ≈ 0.85 of peak) scores proportionally well, landing on something genuinely rare scores low. **Result: correct ordering, finally.** Baseline mean drift **0.4591** (stdev 0.0519) vs adapter mean drift **0.4389** (stdev 0.0147) — the trained adapter now shows *less* drift than the untrained baseline, matching the qualitative read of the actual transcripts. Both conditions still show real, non-degenerate variance.
